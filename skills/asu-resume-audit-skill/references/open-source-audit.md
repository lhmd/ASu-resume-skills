# 开源贡献与角色审计

## 四个必须分开的问题

1. 当事人是否参与过？
2. 哪些工作被提出、合并、发布或持续维护？
3. 获得了什么正式角色？
4. 简历措辞是否准确描述了工作的深度与广度？

## GitHub 取证清单

- `author:<login> repo:<owner>/<repo> is:pr` 搜索结果；
- PR 状态：已合并、关闭未合并、进行中、重复或被替代；
- Commit 与改动文件；
- 代码区域：核心运行时、独立功能、前端、官网、文档、测试、配置、仅注释；
- Review 评论、Request Changes 与最终合并人；
- 变更是否进入 Release；
- 只提 Issue 还是交付实现；
- README 致谢、CODEOWNERS、Team 文件、Maintainer 名单与组织成员关系；
- 提交日期是否落在声称的版本或架构阶段。

常用搜索：

```text
https://github.com/<owner>/<repo>/pulls?q=is%3Apr+author%3A<login>
https://github.com/search?q=org%3A<org>+author%3A<login>+is%3Apr&type=pullrequests
```

使用 GitHub API 时保存查询语句和原始结果数；绝不能把 `closed` 当成 `merged`。

## 贡献深度分级

| 级别 | 常见证据 | 简历安全措辞 |
|---|---|---|
| 0 - 仅可见 | Fork、Star、评论、无实现的 Issue | 关注/讨论该项目 |
| 1 - 边缘贡献 | 文档、错字、官网、小 UI、配置 | 贡献文档/官网/UI 修改 |
| 2 - 有边界实现 | 已合并缺陷修复或功能，责任范围清晰 | 实现/修复具体组件 |
| 3 - 持续子系统所有权 | 多次合并、评审、设计决策、Release | 维护/负责具体子系统 |
| 4 - 项目领导 | 正式核心角色，加上跨模块架构与发布责任 | Maintainer/核心作者/项目负责人 |

正式头衔与贡献深度可能不完全相同。报告应同时保留“头衔真实”和“公开技术范围有限”两类事实。

## 常见夸大信号

### 品牌或 Star 迁移

简历把项目 Star、排名或公司品牌放在个人经历旁。除非能够证明个人造成了其中的实质增量，否则 Star 只能作为项目背景。

### 贡献数量漂白

GitHub Contribution 可能包含 Issue、评论、Fork Commit 与未合并 PR。必须单独统计已合并工件。

### 官网到核心引擎的歧义

官网、文档和 Developer Experience 都是正当贡献。误导发生在简历省略代码区域，让读者推断为核心引擎或算法所有权时。

### 主动合 PR 与角色升格

主动寻找可贡献任务、与 Maintainer 互动、修复前端/官网问题、通过持续贡献获得社区信任都可以是正当成长路线。审计不判断动机，只检查后续措辞：

- 正式角色是否确实授予；
- 角色适用于整个项目还是网站/子项目；
- 简历是否把可见度高的外围工作升级为核心技术深度；
- 社交互动是否被当作无法支持的工作证明。

不能把社交能力本身描述为欺诈。潜在问题在于后续如何描述角色和贡献。

### 全系统架构叙事

候选人可能准确理解整个项目，却只实现其中很小一部分。要求其给出本人负责的设计文档、PR、Commit、测试与线上事件。

## 公平性检查

- 内部公司贡献可能被 squash 或由服务账号提交；
- Maintainer 权限不一定公开；
- README 的“关键贡献者”列表可能只是示例而非穷举；
- 关闭未合并的 PR 仍可显示努力和技术思考，但不能证明已上线影响。

存在这些例外时使用“与公开证据存在张力”，不要写绝对否定。
